## Anti-Patterns Verdict

**Not slop. Not yet trusted-tool grade.** A fluent BEAM developer will trust the words immediately and pause at the frame around them.

**LLM assessment.** The berry system is now committed end-to-end — code themes, asides, mermaid, scrollbar thumbs, selection colour. Nothing reads as unthemed Starlight. The No-Gray Rule holds in every measured surface but one. The One Family Rule holds. No gradient text, no glassmorphism, no hero metrics, no `01/02/03` scaffolding, no tracked eyebrows. The side-stripe is gone, replaced by a full 1px border. `.splash-features` as a `<dl>` is the right answer to the feature-grid anti-reference.

What breaks trust now is **composition, and specifically over-correction from the rework**. Four of the six most serious findings below did not exist before the last pass.

**Deterministic scan.** `website/src` exits 2 with 8 findings — but that scan parsed only 6 of 24 files (the walker excludes `.md`/`.mdx`), so it says nothing about the content pages. Against the fresh `dist` build (verified 34s newer than the newest source file): exit 2, 419 findings, **35 first-party / 384 vendor**.

Of the 35 first-party findings, **28 are false positives, and the detector's reasoning is now traceable**: `single-font` (14) and `flat-type-hierarchy` (14) both fire on line 28 of every built page, which is Astro's inlined Starlight *badge/icon* `<style>` block. The `flat-type-hierarchy` hit reads "12px, 14px, 16px (ratio 1.3:1)" off badge sizing. Measured against the rendered page, the real scale is **h1 42px / h2 35px / h3 29px / body 16px — a 2.63:1 h1:body ratio**. The detector never looked at a heading. `single-font` also fires in-browser on `/advanced/troubleshooting/`, where it *is* reading real type — but that page contains zero `<pre>` blocks, and a rendered census confirms exactly two families site-wide (Spline Sans Variable + Spline Sans Mono Variable). Acting on it would violate DESIGN.md's One Family Rule. Suppress it.

The 7 that stand: `em-dash-overuse` (troubleshooting 20, persistence-operations 12, write-modes 9, introduction 9) and — new since the last pass — **`design-system-color` × 8, all in the mermaid override region of `custom.css:149–244`**: `#3f0019` (×4), `#41001f`, `#54002a`, `#ffdfe6`, `#ffd4de`. I grepped each against DESIGN.md: none are on the published ramp. That's palette drift I introduced and then failed to document, in the same pass where I documented two *other* new tiers.

**Visual overlays.** Injection preflight passed (title writable, `<script>` appended and executed, no CSP); the detector ran in-page on 5 pages: `/` 1, `/introduction/` 12, `/quick-start/` 2, `/guides/write-modes/` 10, `/advanced/troubleshooting/` 22 — mostly `line-length` (~90ch against an 80ch target) plus `tight-leading` on sidebar chrome and `layout-transition` on `body` (vendor-authored, neutralized under `reduce`). **The overlay is no longer visible**: both the asset server and the site dev server were stopped before reporting.

## Overall Impression

The last pass fixed what it aimed at and broke something it didn't aim at. Every P1 from the previous critique is genuinely closed — verified, not assumed. But three of the five priority issues below are regressions from that same pass, and the sharpest one is on the splash: the most important page on the site now renders with **41% of its content band permanently empty**, and the one full-width element at the bottom proves to the reader that the space was available.

The pattern worth naming: **the light theme was verified and the dark theme was declared.** The light mermaid overrides carry `!important` and win; the dark ones don't and silently lose. Dark is the default theme.

## What's Working

1. **The berry code themes are the best thing on the site.** Differentiating tokens on lightness (emphasis) and chroma (voice) instead of hue is a real solution to a single-hue constraint, and it holds under measurement — including inside the terminal frame, where the background steps to `--sl-color-gray-6` and the lowest token still clears 5.08:1. This is the component readers spend the most time on and it is the most carefully made.

2. **Every previous P1 is closed, confirmed by measurement.** 0 contrast failures across **661 element-checks** over 3 pages × 2 themes (lowest passing 5.08 light / 6.09 dark, both 13px syntax tokens). 0 horizontal overflow across 12 page/width combinations. **0 `<pre>` elements clip content at any width**, including 390px — the 742px-of-hidden-code failure is gone. All 5 focus rings measured under real keyboard `Tab` at **9.21–10.67:1**, no `outline: none` anywhere. Both mermaid diagrams render in both themes with `<title>`/`<desc>` wired via `aria-labelledby`/`aria-describedby`. 0 unguarded animations. `/og.png` returns 200 at exactly 1200×630.

3. **"Compared to the alternatives" still earns the adoption.** Four bullets, competitors named and linked, each described accurately, ending with a link to Limitations *before* the install instructions. For a comparison-shopping BEAM developer this is the highest-value 80 words on the site, and it converts by not selling.

## Priority Issues

### [P1] The splash wastes 41% of its content band — a regression from the last pass
**What**: I verified this directly at 1440px. Content band 180→1260px. Prose right edge **845px**. Code frame right edge **778px**. Feature grid right edge **1260px**. That's a **595px dead gutter**, a **67px stagger** between prose and the code block directly below it, and a feature grid **415px wider than the prose above it**.
**Why it matters**: This is the first frame an evaluator sees, before a word is read. The previous critique complained about a ragged gutter *inside* the column; the fix promoted that gutter to the page level, and the one full-width element advertises the unused space. A half-empty landing page reads as unfinished — the "toy project" anti-reference, arriving pre-verbally.
**My call, and it was wrong**: I considered exactly this last turn and decided "aligned-and-narrow is clearly better than ragged." An independent review calls it the most visible flaw on the site.
**Fix**: Constrain the container, not the children. Set `max-width` on `[data-has-hero] .content-panel > .sl-markdown-content` and drop the per-element rule at `custom.css:32–36`; give `.splash-features` `max-width: none` so its break-out is deliberate. This fixes the 67px stagger for free — that stagger exists only because `70ch` resolves against a different font metric inside the code frame.
**Suggested command**: `/impeccable layout`

### [P1] Dark-mode mermaid theming is dead CSS
**What**: Verified directly. `pre.mermaid[data-processed]` computes **`rgba(255, 255, 255, 0.02)`** in dark, not the declared `#3f0019` (`custom.css:174–181`) — astro-mermaid's vendor default wins. The dark edge-label chips (`custom.css:188–192`) are inert too; `.labelBkg` computes **`rgba(52,0,20,0.5)`**, the `edgeLabelBackground` value from `astro.config.mjs`, so labels sit in darker holes punched through the diagram.
**Why it matters**: Dark is the default theme, and these diagrams are the only visual explanation of the ETS/DETS mechanism — the artifact an evaluator screenshots into their team's Slack. A 2%-white film is also the single neutral-white surface in a system that defends the No-Gray Rule everywhere else. The two assessments disagreed here (B measured the labels as *legible*, which they are); both are right — it's a system-consistency failure, not an a11y one.
**Fix**: Scope the dark rules the way the light ones are scoped so they win identically: `:root[data-theme='dark'] pre.mermaid[data-processed] { … }`. Cleaner still, change `edgeLabelBackground` in `astro.config.mjs` from `#340014` to `#3f0019` so the chip and its container match at source.
**Suggested command**: `/impeccable colorize`

### [P1] The Persistence Flow diagram contradicts its own page
**What**: `advanced/persistence-operations.md`. Mermaid stacks the `wt` subgraph above `wb` despite `wb` being declared first, so the diagram reads WriteThrough→WriteBack while the prose directly beneath reads WriteBack→WriteThrough. Separately, the WriteBack chain draws `DETS -->|"sync()"| filesystem` while the same page's `## sync` section says "In WriteBack mode `sync()` is rarely needed."
**Why it matters**: This is the canonical durability reference. A reader who scans the diagram before the prose leaves with the two write modes inverted and a wrong model of when `sync()` matters — on the page that decides whether they lose data. The prose half of this contradiction is copy I added last pass.
**Fix**: Force diagram order to match prose order, and relabel the WriteBack terminal edge — `save()` is what advances WriteBack data per the page's own layer table; `sync()` belongs only on the WriteThrough chain.
**Suggested command**: `/impeccable clarify`

### [P2] The rework left a two-voice site
**What**: Sentence case on the pages I touched (`index.mdx`, `introduction.mdx`, `installation.mdx`, parts of `persistence-operations.md`); Title Case on the five I didn't (`set-tables.md`, `bag-tables.md`, `duplicate-bag-tables.md`, `write-modes.md`, `limitations.md`). Confirmed collision: **`set-tables.md:103` "Atomic Counters"** vs **`common-patterns.md:76` "Atomic counters"** — same feature, adjacent sidebar entries. `persistence-operations.md` does it within one page: "Durability story" next to "Persistence Flow".
**Why it matters**: The sidebar and ToC put these side by side. This is the "pause at every subtly-off component" tell — individually invisible, cumulatively corrosive to the impression of care the code themes worked hard to build. And search traffic lands on guides far more often than on a splash, so the un-reworked pages are probably what most readers see first.
**Fix**: Sentence case everywhere except proper nouns and API identifiers (`WriteBack`, `DETS`, `with_table`), including the `label:` entries in `astro.config.mjs`.
**Suggested command**: `/impeccable clarify`

### [P2] Quick Start is the thinnest page on the site and it is the primary CTA target
**What**: 212 words, two numbered steps, no run step, no expected output — and it re-uses the same `set.open` sample that already appears on `index.mdx` and `introduction.mdx`, making three near-identical first samples across the first three pages of the funnel. Meanwhile `installation.mdx` (321 words, which I expanded last pass) holds the runnable end-to-end verify program.
**Why it matters**: PRODUCT.md's success metric is *completed quick-starts* and the design principle is *fast path to first table*. The page owning both is the emptiest, and after the rework it reads as padded rather than fast. I fixed the code block on this page and never asked whether the page itself was doing its job.
**Fix**: Move the verify program into Quick Start as step 3 — run it, see `shelf is working`, run it *again* and watch the data persist. That second-run demonstration is the single most convincing thing this library can show, and right now it's a one-line aside on `/introduction/`.
**Suggested command**: `/impeccable onboard`

## Minor Observations

- **The Designed Code Rule claim I made last turn was overstated.** Verified: `getComputedStyle(pre).fontFamily` is still the browser `monospace` at 14.4px. The `codeFontFamily` styleOverride did not reach the `<pre>`. It doesn't affect a single rendered glyph — every `<pre>` is `pre > code > span` with no direct text nodes, and `<code>` correctly computes Spline Sans Mono at 13px — but the `<pre>` remains the one element where the declaration is missing, exactly as the first critique described. A latent trap if content ever lands directly in a `<pre>`.
- **The berry severity ramp exists in CSS but not on screen.** Source census: only `note` (×4) and `caution` (×2) are used anywhere. `tip` and `danger` are styled and never used. Between the two that are used, the dark background delta is **1.07:1** — I measured it. Worse, `note` against the page ground is **1.06:1**, so it barely reads as a panel at all. Either the site needs a real `danger` (the WriteBack data-loss warning is the obvious home) or the ramp should collapse to two honestly-distinct tiers.
- `advanced/troubleshooting.md` — the page most in need of a "this will lose data" marker — contains zero asides.
- Inline `<code>` inside `h2` computes **35px**, so troubleshooting's seven headings render as oversized filled pink chips, most wrapping to two lines; "What is `FileSizeLimitExceeded`?" strands its question mark. The ToC strips the styling, so headings and ToC look like two different documents.
- `berry-code-themes.mjs` documents its light ratios against `#fff3f5`, but the terminal frame overrides the background to `--sl-color-gray-6`; string tokens there measure 5.08:1, not the documented 5.50:1. The light comment token measures `#82556a` / 5.61:1 in the DOM rather than the documented `#8a5a70` / 5.13:1. Reconcile so the file's ratios stay auditable.
- Mermaid nodes render with 0 border-radius while every other surface uses `0.5rem` — the only square-cornered thing on the site.
- The skip-link focus ring is clipped by the top of the viewport (`outline-offset: 3px` on an element at `top: 0`).
- `og:type` is `article` on the home page, where `website` is conventional; `theme-color` is absent, so mobile browser chrome won't pick up the berry ground.
- `set-tables.md`, `bag-tables.md` and `duplicate-bag-tables.md` share a near-identical six-heading skeleton at 378–510 words each — structurally correct, but three templated pages in a row read as padding to someone skimming the sidebar.
